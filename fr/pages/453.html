Vigilo — Plan de projet complet

Nous exécutons votre application à chaque pull request et identifions la cause de la défaillance plutôt que de deviner.

Plan d'exécution complet pour un nouveau projet numérique : l'idée, le public cible, le produit, le modèle économique, le plan de diffusion et les risques. Le projet est en cours de développement et n'a pas encore été lancé.

Plan du produit : Examen du code par exécution réelle (Runtime AI Review)

Problème : L'analyse statique lit le code sans l'exécuter. Elle détecte les erreurs de syntaxe, mais ignore les erreurs de comportement : un parcours de requête cassé, un bouton qui ne fonctionne pas, un processus de connexion défaillant ou une condition aux limites qui échoue avec des données réelles. Résultat : une course vers la production avec un fort taux de retour pour chaque rapport de bogue.

1) Public cible

· Segment · Taille · Douleur principale · Besoin recherché ·

· Équipes de développement (5–50 développeurs) en phases de livraison quotidiennes · La plus grande · Revues de PR lentes, bogues comportementaux apparaissant après fusion · CI qui bloque automatiquement les PR défectueux avec des preuves prêtes à être transmises ·

· Développeurs SaaS et e-commerces · Grande · Augmentation du support client due aux bogues à l'exécution · Scénarios E2E générés automatiquement à chaque modification ·

· Équipes Frontend/Full-stack · Moyenne · Absence d'un environnement macOS/Windows reproduisant la production en local · Exécution réelle dans un runner isolé et documentée ·

· Testeurs QA manuels · Petite · Répétition des cas de test manuels · Transformation de l'exploration manuelle en scénarios reproductibles ·

· Équipes géographiquement distribuées (y compris les marchés MENA) · Moyenne · Temps de réaction longs entre les régions · Preuves visuelles (vidéo + journaux) permettant d'éviter une reproduction locale ·

Cible interne : principalement les développeurs d'entreprises et de produits numériques (Dev/Full-stack), puis au fil du temps les opérateurs QA et les équipes de livraison.

2) Points de différenciation (pourquoi choisir ce produit)

1. Exécution dans votre propre infrastructure CI : fonctionne sur un runner isolé (self-hosted) ou sur le runner cloud de votre choix — aucun code n'est envoyé vers un cloud tiers. Avantage : meilleure confidentialité, coûts réduits et conformité facilitée.

2. Exécution incrémentielle : une carte des dépendances entre parcours, composants et actions permet d'exécuter uniquement les scénarios impactés par la modification — réduction considérable du temps et du coût par rapport à une exécution complète.

3. Ensemble de preuves vérifiables : vidéo WebM + journaux Console + fenêtre Réseau + captures DOM + traces de pile avec numéros de ligne, fichiers et sélecteurs précis — un rapport prêt à être transformé en ticket de support ou en rapport de bogue.

4. Reproduction déterministe : seed fixe + simulation du temps, du réseau et du fuseau horaire + versions figées ⇒ le même échec se reproduit dans les mêmes conditions, sans flakiness aléatoire.

5. Conçu pour CI, non comme une plateforme séparée : sorties SARIF et JUnit + commentaire automatique sur la PR + possibilité de bloquer la fusion via Branch Protection. Aucune modification des habitudes de l'équipe n'est requise.

6. Flexibilité des coûts : BYO-LLM (avec votre propre clé) + mode « sans LLM » pour les scénarios existants + plafond clair des tokens et de la durée par exécution.

7. Noyau open source sous licence adaptée + version entreprise auto-hébergée : gratuit en permanence pour les projets open source, et commercialisable aux entreprises interdisant l'utilisation d'un SaaS externe.

8. Conception entièrement nouvelle : architecture indépendante (CLI + Agent + couche d'adaptateurs), identité visuelle inédite et modèle d'interaction « Evidence-first » sans copie d'un produit existant.

3) Périmètre de la première version (8 tâches maximum)

1. CLI + GitHub Action / GitLab CI : une commande unique vigilo run --pr 128 exécute le contrôle dans un runner isolé, avec l'option --local pour un lancement sur la machine du développeur.

2. Environnement d'exécution sécurisé : conteneur temporaire sans secrets, ressources limitées, réseau isolé par défaut (deny-all avec listes blanches) et suppression automatique à la fin de l'exécution.

3. Génération de scénarios depuis la PR : analyse du diff + description de la PR + structure du projet (openapi/libellés d'écrans) pour générer des étapes de navigation exécutables (driver de type Playwright écrit de zéro).

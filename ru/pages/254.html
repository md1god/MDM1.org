Mizan Pay — полный план проекта

Все платёжные сети и выписки по счетам в одном пайплайне.

Полный план реализации нового цифрового проекта: идея, аудитория, продукт, модель монетизации, план распространения и риски. Проект находится в разработке и ещё не запущен.

Продуктовый план: платформа унификации инициирования платежей и выписок по счетам

1) Целевая аудитория

• Финтех-инженеры и небольшие платёжные компании (PSP), которые хотят отправлять платежи ACH/SEPA/FedNow/SWIFT/RTP без создания валидаторов для каждой сети.

• Небольшие цифровые банки (Neobanks) и команды казначейства (Treasury), которым нужна автоматическая сверка выписок camt с платёжными поручениями.

• Разработчики бухгалтерских систем и ERP, которые хотят генерировать файлы банковских платежей и читать выписки по счетам внутри своих продуктов.

• Компании электронной коммерции и фрилансеры между странами, работающие с несколькими валютами и сетями.

2) Преимущества (почему выбирают наш продукт)

• Полная среда моделирования (Sandbox): фиктивные банковские данные и генератор выписок, так что разработчик начинает в тот же день без банковского договора.

• Автоматическая сверка: автоматическая связь между платёжными поручениями и movements выписок с готовым отчётом о расхождениях, а не просто генерация файлов.

• Точность на уровне полей: проверка IBAN/BIC/routing numbers, дат валидности и лимитов сумм с понятными сообщениями об ошибках, указывающими на номер поля.

• Работает локально (self-hosted) с управляемой облачной версией — без привязки и фиксации на одном провайдере.

• SDK со строгой типизацией (TypeScript/Python) и интерфейс CLI с интерактивной документацией и сравнением эталонных форматов ISO 20022.

• Встроенный журнал аудита и подготовка данных для комплаенса (AML checks) как начальный шаг перед отправкой.

3) Объём первой версии (не более 8 задач)

1. REST API для генерации и проверки сообщений pain.001, pain.008 и camt.052/053/054.

2. Движок правил для проверки номеров счетов, валют, дат и лимитов сумм перед генерацией.

3. Адаптеры (Adapters) для четырёх сетей: ACH, SEPA, FedNow/RTP, SWIFT — с файлом вывода для каждой сети.

4. Интерфейс сверки (Reconciliation), связывающий выписки с платёжными поручениями и показывающий расхождения.

5. Среда Sandbox с генератором фиктивных банковских данных и готовыми для тестирования выписками.

6. CLI + пакеты npm и Python с готовыми примерами.

7. Лёгкая веб-панель: журнал платежей, статус сверки и ошибки проверки.

8. Интерактивная документация + система прав и базовые ключи API.

4) Ценообразование и модель прибыли

• Ядро с открытым исходным кодом (лицензия MIT): локальное использование и тестирование бесплатны навсегда — модель free-to-start.

• Free: до 1 000 сообщений в месяц в облаке + безлимитный Sandbox.

• Pro — 49$ в месяц: 25 000 сообщений, автоматическая сверка, экспорт отчётов, поддержка по почте.

• Scale — 299$ в месяц: практически неограниченные сообщения, расширенный журнал аудита, SLA, интеграция с ERP.

• Self-hosted / Enterprise: годовая лицензия + поддержка и обновления форматов ISO 20022.

• Дополнительная выручка: консалтинг по интеграции (onboarding) и платные обучающие курсы.

5) План глобального распространения через бесплатные каналы

• Открытый репозиторий GitHub + Show HN и Reddit (r/fintech, r/programming) для охвата разработчиков.

• Сравнительные статьи в SEO: «pain.001 vs pain.008», «как читать camt.053» — долгосрочное привлечение органического поиска.

• Dev.to, Medium и YouTube: короткие уроки «создай первый платёж SEPA за 10 минут».

• X/LinkedIn: технические треды на английском и арабском о проблемах банковской интеграции.

• Product Hunt при запуске облачной версии + бесплатные руководства в репозиториях сообщества.

• Локальные группы Telegram/WhatsApp для первых рынков (Залив, Египет, Германия) и участие в meetups и hackathons.

6) Риски (юридические и технические)

• Юридические: продукт не хранит деньги — следует избегать его классификации как money transmitter; соблюдение AML/KYC остаётся на клиенте. Плюс GDPR/защита данных счёта, списки санкций (sanctions screening) и конфиденциальность данных по странам (например, саудовский/эмиратский закон о защите данных).

• Технические: различия версий форматов ISO 20022 и требований каждого банка и преобразователя (Mapper); ошибки таймингов, сроков и категорий (Business Day/Cut-off); конфиденциальность ключей API и подделка сообщений; риски будущих обновлений схем, требующих обратно совместимых версий.

• Операционные: зависимость от одного облачного провайдера и сложность поддержки множества локальных сетей без партнёров.

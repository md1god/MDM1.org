مِحْكَم — Plan de projet complet

Avant de cliquer sur Merge, sachez quelle ligne mérite un œil humain et quel fichier peut passer en toute sécurité.

Plan complet : idée, public, produit, revenus, diffusion, risques. Projet en construction, non lancé.

1) Public cible

• Équipes 3-15 devs, 10-40 pull requests/semaine, pas de relecteur permanent : « ceci passe, cela demande un œil humain avant 18 h ».

• Ingénieurs plateforme/DevOps : protéger les branches et les règles de merge automatique ; //! écrire les règles YAML à la main, puis voir une migration sans rollback passer.

• Open source : 20+ pull requests/semaine de personnes ignorant la structure ; risque : petit changement dans un fichier d'authentification ou un script de suppression de données.

• Fintech, health, SaaS audités : « l'IA a approuvé » ne suffit pas ; journal : règle, ligne, personne ayant poursuivi.

• Devs indépendants, longues diffs après minuit : 300 lignes/12 fichiers triés via fr.triage en minutes, pas ligne par ligne.

2) Points forts (pourquoi choisir notre produit)

• Pas un « rédacteur de commentaires » mais une « passerelle de décision » : 3 scores (régression, authentification, perte de données) plus un rapport d'éligibilité au merge automatique Markdown/JSON.

• Preuve visible : clic sur l'alerte → fichier et ligne dans le diff. Pas de boîte noire : « supprimer une colonne en migration sans rollback = 85 ».

• Collage d'abord, sans install ni permissions : diff collé → résultat <10 s, dépôt lié après ; essai 1 j → 5 min.

• Vérifie la réversibilité : feature flag ? étape de rollback ? schéma DB modifié ? Axés sur le style, ils l'oublient.

• Revue humaine ≤5 fichiers triés par gravité, pas « relisez tout ». Ex. : 14 fichiers, 3 en Human review, reste auto.

• Rapport bilingue arabe/anglais, même structure : joint à la pull request Riyad-Berlin, sans traduction.

3) Périmètre de la première version (8 tâches maximum)

1. Deux entrées : lien de pull request ou texte unified diff collé ; encodage et lignes longues traités (tâche 1).

2. Analyseur diff léger : carte fichiers/lignes/méthodes, sans exécuter de code (tâche 2).

3. Moteur de règles local : 4 risques, score 0-100 par catégorie + règle appliquée (tâche 3).

4. Preuves + liste « fichiers à œil humain » ≤5, lien interne vers la ligne (tâches 4-5).

5. Éligibilité : « tests OK, aucun changement sensible, ≥1 relecteur humain » ; export Markdown/JSON (tâches 6-7).

6. Interface web arabe/anglaise, lien lecture seule, 20 analyses/mois gratuites, objectif <10 s (tâche 8).

4) Tarification et modèle de revenus

• Gratuit : 20 analyses/mois, diff ≤500 lignes, export Markdown, sans carte ; 3 analyses avant compte.

• Pro 9 $/dev/mois : 300 analyses, GitHub en lecture seule, modèles strict/équilibré/souple, journal 90 j, JSON.

• Team 49 $/mois jusqu'à 10 devs : GitHub App checks, politiques par dépôt, journal d'audit, alerte Slack/Zulip si « non décisif ».

• Enterprise sur demande : auto-hébergement, SSO/SAML, rétention personnalisée, règles type « /payments = 2 approbations ».

• Compteur transparent : requête échouée/annulée non déduite, alerte à 80 %.

• V1 : pas de bouton de merge ; éligibilité seule, décision humaine. Puis merge auto cadré par politique.

5) Plan de diffusion mondiale via des canaux gratuits

• SEO : « checklist risques diff avant merge », « détecter migration sans rollback » ; outil de collage gratuit en fin de page.

• Product-led growth : rapport partageable en lecture seule ; diffusion dans l'équipe quand l'utilisateur partage sur Slack avant la revue.

• Communautés : Show HN, dev.to, Hashnode, r/webdev, newsletter arabe LinkedIn « Relisez une pull request OSS en 5 min ».

• Intégrations gratuites : GitHub Marketplace lecture seule, puis VS Code extension, webhook Zulip/Slack pour l'OSS.

• « triage hebdomadaire » : 3 projets OSS, court rapport, mention « aide, pas verdict ».

• Croissance : activation = 1er rapport <5 min, rétention = 3 analyses/2 sem., parrainage = 1 lien partagé/utilisateur actif.

6) Risques (juridiques et techniques)

• Juridique : diff confidentiel ; pas de stockage >24 h, chiffrement en transit, GDPR, bouton supprimer, page « aide, sans garantie ».

• Technique : GitHub API ~5 000 req/h peut bloquer ; collage d'abord, cache, jeton READ-ONLY, file d'attente.

• Décision : fausses alertes = confiance perdue ; seuil 70, « non décisif » au lieu de refus, taux d'approbation humaine hebdo.

• Entrées : clés API/mots de passe possibles ; masquage secrets avant affichage et appel externe, valeurs → astérisques.

• Économique : coût LLM ; règles en local, modèle pour résumé optionnel, objectif <0,01 $/analyse.

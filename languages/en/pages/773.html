Mihkam — Complete Project Plan

Before you press Merge, know which line deserves a human eye and which file can pass safely.

Plan for a new digital project: idea, audience, product, revenue model, distribution, risks. Not launched.

1) Target audience

• Teams of 3–15 devs handling 10–40 change requests/week, no reviewer always available; need: "This can pass; this needs a human eye before 6 p.m."

• Platform/DevOps engineers guarding branches and auto-merge rules; hand-write YAML, then find a migration without rollback slipped through.

• Open-source owners with 20+ pull requests/week from newcomers, fearing a small change in an auth file or deletion script will pass.

• fintech, health, SaaS firms under internal audit; "AI approved" is not enough — they want a record of rule, line, and who pushed it.

• Devs reviewing long diffs after midnight; 300 lines in 12 files need fr.triage in minutes, not line-by-line reading.

2) Differentiators

• Not a "comment writer" but a "decision gate": three scores (regression, authentication, data loss) plus Markdown/JSON merge eligibility.

• Evidence per score: click warning, open file and exact line in diff. No black box; e.g., "Delete a column in a migration without a reverse step = 85".

• Paste-first, no install or permissions: result in under 10s; connect repo later. Trial: a day → 5 minutes.

• Explicit reversibility check: feature flag? rollback? schema change? Most tools forget this.

• Human review capped at 5 files by severity, not "review everything": e.g., 14 files, only 3 need Human review.

• Bilingual report (Arabic/English), same structure, attachable to a change request in a Riyadh–Berlin team, no manual translation.

3) First-release scope (8 tasks maximum)

1. Two inputs: change-request link or pasted unified diff; safe encoding, long lines (task 1).

2. Lightweight diff parser mapping affected files, lines, methods; no code execution (task 2).

3. Local rules engine: four risks, 0–100 per category with rule name (task 3).

4. Evidence layer plus "files needing a human eye" list capped at 5, with line link (tasks 4, 5).

5. Eligibility report: "all tests pass, no sensitive change, one human reviewer", plus Markdown/JSON export (tasks 6, 7).

6. Arabic/English web UI, read-only share link, 20 free scans/month, under 10s analysis (task 8).

4) Pricing and revenue model

• Free: 20 scans/month, diff to 500 lines, Markdown export, no card; 3 scans before signup.

• Pro: $9/dev/month: 300 scans, GitHub read-only, policy templates (strict/balanced/lenient), 90-day log, JSON.

• Team: $49/month up to 10 devs: GitHub App checks, repo policies, audit log, Slack/Zulip notice for "non-decisive" changes.

• Enterprise: on request — self-hosting, SSO/SAML, custom retention, rules like "two approvals for /payments".

• Transparent counter: failed/cancelled requests cost no credit, alert at 80%; builds subscription trust.

• Release 1 never presses merge; it only issues "eligibility"; human decides. Later: restricted auto-merge under team policy.

5) Free global distribution channels

• SEO pages: "diff risk checklist before merging", "how to detect a migration without rollback"; each ends with a free paste tool.

• Product-led growth: shareable read-only result link spreads in teams when posted in Slack before reviews.

• Communities: Show HN, dev.to, Hashnode, r/webdev, plus Arabic weekly LinkedIn newsletter "Review an open-source change request in 5 minutes", with real results.

• Free integrations: GitHub Marketplace with read-only permission, then VS Code extension and webhooks to Zulip/Slack for open source.

• "Weekly triage": pick 3 open-source projects, publish a short risk report, noting it is an aid, not a verdict.

• Growth metrics: activation = first report in 5 min, retention = 3 scans in two weeks, referral = one share link/user.

6) Risks (legal, technical)

• Legal: diffs may be confidential; "no storage after 24h", encryption in transit, GDPR compliance, immediate delete, and a page: outputs are aids, not guarantees of vulnerability-free code.

• Technical: GitHub API limits (~5,000 requests/hour) may interrupt scanning; use paste-first, caching, READ-ONLY token, queue past the limit.

• Decision accuracy: false alarms destroy trust fastest; threshold 70, "non-decisive" instead of rejection, weekly human-approval measurement.

• Input security: diffs may contain API keys or passwords; scrub secrets before display and external model calls, replacing values with asterisks.

• Economic: LLM cost may exceed the subscription; process rules locally, call model only for optional summarization, under $0.01/scan.

مِحْكَم — Vollständiger Projektplan

Bevor du auf Merge klickst, wisse, welche Zeile ein menschliches Auge braucht und welche Datei sicher durchgehen kann.

Plan digitales Projekt: Idee, Zielgruppe, Produkt, Geschäftsmodell, Rollout, Risiken. Noch im Aufbau, nicht live.

1) Zielgruppe

• Teams mit 3–15 Entwicklern, 10–40 Änderungsanträgen/Woche, ohne Reviewer: „Das kann durchgehen, das braucht vor 18 Uhr ein Auge“.

• Platform-/DevOps Engineers, Branch-Schutz und Merge-Regeln; //! YAML von Hand, dann merken: migration ohne rollback-Pfad durchgerutscht.

• Open-Source-Betreiber, >20 Contributions/Woche von Unbekannten: Sorge vor kleiner Änderung in Auth-Datei oder Datenlösch-Skript.

• Fintech-/Health-/SaaS mit Audit: „KI hat zugestimmt“ reicht nicht; Protokoll mit Regel, Zeile, Person.

• Freelancer nach Mitternacht bei langen diffs: 300 Zeilen/12 Dateien brauchen fr.triage in Minuten statt Zeile für Zeile.

2) Alleinstellungsmerkmale (warum unser Produkt)

• Entscheidungs-Tor statt Kommentar-Schreiber: drei Werte (Regression, Authentifizierung, Datenverlust) plus Eignungsbericht für automatisches Merge als Markdown oder JSON.

• Beleg pro Wert: Klick öffnet Datei und Zeile im diff. Keine Blackbox; z. B. „Spalte in migration ohne rollback-Schritt löschen = Wert 85“.

• Einfügen zuerst, ohne Installation/Rechte: diff einfügen, Ergebnis <10 Sekunden, Repository später. Erprobung: 1 Tag → 5 Minuten.

• „Rückfährbarkeit“ explizit: feature flag? rollback-Schritt? DB-Schema geändert? Andere Tools achten nur auf Stil.

• Max. 5 Dateien nach Schwere statt „Prüfe alles“; 14 Dateien, nur 3 brauchen Human review, Rest automatisch sicher.

• Zweisprachig (Arabisch/Englisch), gleiche Struktur, im Team Riad–Berlin dem Antrag ohne Übersetzung anhängbar.

3) Umfang der ersten Version (maximal 8 Aufgaben)

1. Zwei Eingaben: Link zum Änderungsantrag oder eingefügter unified diff, sicher bei Zeichensätzen und langen Zeilen (Aufgabe 1).

2. Leichter diff-Parser: Karte aus Dateien, Zeilen, Methoden, ohne Codeausführung (Aufgabe 2).

3. Lokale Regel-Engine: vier Klassen, Wert 0–100 je Klasse plus Regelname (Aufgabe 3).

4. Beleg-Ebene plus Liste „Dateien mit menschlichem Auge“, max. 5, Zeilen-Link (Aufgaben 4 und 5).

5. Eignungsbericht: „Tests grün, keine sensible Änderung, min. 1 Reviewer“, Export Markdown/JSON (Aufgaben 6 und 7).

6. Arabisch/englische UI, schreibgeschützter Share-Link, 20 Prüfungen/Monat gratis, Analyse <10 Sekunden (Aufgabe 8).

4) Preis- und Geschäftsmodell

• Gratis: 20 Prüfungen/Monat, diff bis 500 Zeilen, Markdown-Export, ohne Kreditkarte; 3 Prüfungen vor Konto.

• Pro: 9 USD/Entwickler/Monat, 300 Prüfungen, GitHub nur lesend, Policy-Vorlagen (streng/ausgewogen/flexibel), 90 Tage Log, JSON-Export.

• Team: 49 USD/Monat bis 10 Entwickler, GitHub App checks, Policy pro Repo, Audit-Log, Slack/Zulip bei „nicht entscheidend“.

• Enterprise auf Anfrage: Self-Hosting, SSO/SAML, eigene Aufbewahrung, Regel wie „/payments: zwei Zustimmungen“.

• Zähler transparent: Fehlschlag/Abbruch kostet nichts, Warnung bei 80 %.

• Kein Merge-Button in V1: nur „Eignung“, Mensch entscheidet. Später automatischer Merge an Team-Policy.

5) Globaler Rollout-Plan mit kostenlosen Kanälen

• SEO: „Checkliste für diff-Risiken vor dem Merge“, „migration ohne rollback erkennen“; Seite endet mit Einfüge-Tool.

• Product-led growth: Bericht per schreibgeschütztem Link teilbar, verbreitet per Slack vor dem Review-Meeting.

• Communities: Show HN, dev.to, Hashnode, r/webdev, arabischer LinkedIn-Newsletter „Open-Source-Änderungsantrag in 5 Minuten prüfen“, echte Ergebnisse.

• Integrationen: GitHub Marketplace erst nur lesend, später VS Code extension, webhook zu Zulip und Slack.

• „wöchentliches triage“: 3 Open-Source-Projekte, kurzer Risikobericht, klar als Helfer, nicht Urteil.

• Kennzahlen: Aktivierung = erster Bericht in 5 Minuten, Retention = 3 Prüfungen/2 Wochen, Empfehlung = min. 1 Link pro aktivem Nutzer.

6) Risiken (rechtlich und technisch)

• Rechtlich: diff kann vertraulich sein; „keine Speicherung nach 24 Stunden“, Verschlüsselung bei Übertragung, GDPR, Sofort-Lösch-Button, Hinweis: Ausgaben helfen, keine Fehlerfreiheit garantiert.

• Technisch: GitHub API (~5000 Anfragen/Stunde) kann stoppen; Einfüge-Pfad, Cache, nur READ-ONLY-Token, Warteschlange.

• Genauigkeit: Fehlalarme zerstören Vertrauen; Schwelle 70, „nicht entscheidend“ statt Ablehnung, wöchentliche Zustimmungsrate.

• Eingaben: diff kann API-Schlüssel/Passwörter enthalten; secrets-Maske vor Anzeige und externem Modell, Werte durch Sterne.

• Wirtschaftlich: LLM-Kosten können Abo übersteigen; Regeln lokal, Modell nur optional, Ziel <0,01 USD pro Prüfung.

مِحْكَم — Rencana Proyek Lengkap

Sebelum menekan Merge, ketahui baris mana yang layak mendapat mata manusia dan file mana yang bisa lolos dengan aman.

Rencana proyek digital baru: ide, audiens, produk, model pendapatan, distribusi, risiko. Masih dibangun, belum diluncurkan.

1) Audiens Target

• Tim 3-15 pengembang, 10-40 permintaan perubahan/minggu, tanpa reviewer tetap. Butuh alat: «Ini lolos, ini butuh mata manusia pukul 6 sore.»

• Insinyur platform/DevOps penjaga branch dan merge otomatis; //! aturan YAML ditulis manual, migration tanpa rollback ikut lolos.

• Pemilik open source, >20 kontribusi/minggu dari orang asing struktur proyek; takut perubahan di file autentikasi atau skrip hapus data lolos.

• Fintech, health, SaaS diaudit internal; «AI menyetujui» tak cukup: mau catatan aturan apa, baris mana, siapa yang lanjut.

• Pengembang lepas, diff panjang lewat tengah malam; 300 baris/12 file butuh fr.triage dalam menit, bukan baca dari awal.

2) Nilai Unik (Mengapa produk kami)

• Bukan «penulis komentar», tapi «gerbang keputusan»: 3 skor (regresi, autentikasi, kehilangan data) plus laporan merge otomatis Markdown/JSON.

• Tiap skor ada bukti: klik peringatan → file dan baris di diff terbuka. Tanpa kotak hitam; «Hapus kolom di migration tanpa rollback = 85».

• Tempel dulu, tanpa instalasi/izin: hasil <10 detik, repository menyusul. Waktu coba: sehari jadi 5 menit.

• Cek eksplisit rollback: feature flag? langkah rollback? skema database berubah? Alat lain sering lupa.

• Maksimal 5 file untuk Human review, diurutkan menurut risiko, bukan «tinjau semua». Contoh: 14 file, 3 butuh review.

• Laporan Arab/Inggris, struktur sama; dilampirkan ke permintaan perubahan tim Riyadh-Berlin tanpa terjemahan.

3) Ruang Lingkup Versi Pertama (maksimal 8 tugas)

1. Dua masukan: tautan permintaan perubahan atau unified diff ditempel; encoding dan baris panjang aman (Tugas 1).

2. Penganalisis diff ringan: peta file, baris, metode terdampak tanpa eksekusi kode (Tugas 2).

3. Mesin aturan lokal: 4 risiko, skor 0-100 per kategori + nama aturan (Tugas 3).

4. Lapisan bukti + daftar «file butuh mata manusia» maksimal 5, tautan ke baris (Tugas 4-5).

5. Laporan kelayakan: «tes lulus, tanpa perubahan sensitif, minimal satu reviewer manusia», ekspor Markdown/JSON (Tugas 6-7).

6. Web Arab/Inggris, tautan berbagi read-only, gratis 20 pemeriksaan/bulan, target <10 detik (Tugas 8).

4) Harga dan Model Pendapatan

• Gratis: 20 pemeriksaan/bulan, diff ≤500 baris, ekspor Markdown, tanpa kartu kredit; 3 pemeriksaan sebelum akun.

• Pro 9 dolar/pengembang/bulan: 300 pemeriksaan, GitHub read-only, templat kebijakan (ketat/seimbang/longgar), riwayat 90 hari, JSON.

• Team 49 dolar/bulan sampai 10 pengembang: GitHub App checks, kebijakan per repository, log audit, notifikasi Slack/Zulip untuk «tidak konklusif».

• Enterprise sesuai permintaan: self-hosting, SSO/SAML, retensi khusus, aturan kustom mis. «/payments butuh dua persetujuan».

• Penghitung transparan: gagal/dibatalkan tak memotong saldo, peringatan di 80%. Membangun kepercayaan.

• Versi pertama tak menekan merge; hanya «kelayakan», manusia memutuskan. Nanti merge otomatis sesuai kebijakan.

5) Distribusi Global via Kanal Gratis

• SEO praktis: «Daftar risiko diff sebelum merge», «Deteksi migration tanpa rollback»; tiap halaman ada alat tempel gratis.

• Product-led growth: laporan via tautan read-only, menyebar di tim saat dikirim ke kanal Slack sebelum rapat tinjauan.

• Komunitas: Show HN, dev.to, Hashnode, r/webdev, newsletter Arab LinkedIn «Tinjau perubahan open source dalam 5 menit».

• Integrasi gratis: GitHub Marketplace read-only dulu, lalu VS Code extension, webhook Zulip dan Slack untuk open source.

• «triage mingguan»: 3 proyek open source, laporan ringkas risikonya, ditegaskan sebagai pembantu, bukan keputusan akhir.

• Metrik: aktivasi = laporan pertama 5 menit; retensi = 3 pemeriksaan/2 minggu; rujukan = ≥1 tautan berbagi/pengguna aktif.

6) Risiko (Hukum dan Teknis)

• Hukum: diff bisa rahasia; «tanpa penyimpanan setelah 24 jam», enkripsi saat transit, kepatuhan GDPR, tombol hapus instan, keluaran bukan jaminan aman.

• Teknis: batas GitHub API (~5000 permintaan/jam); solusinya tempel dulu, cache, token READ-ONLY, antrean saat penuh.

• Akurasi: alarm palsu merusak kepercayaan; ambang 70, label «tidak konklusif» bukan penolakan, persetujuan manusia diukur mingguan.

• Masukan: diff bisa berisi kunci API/kata sandi; pemindaian secrets sebelum tampil dan sebelum panggilan model eksternal, nilai jadi bintang.

• Ekonomi: biaya LLM bisa melebihi langganan; aturan lokal, model hanya ringkasan opsional, target <0,01 dolar per pemeriksaan.
